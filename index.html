Viridium Linux

Viridium Linux is a minimal, Arch-based Linux distribution.

It uses the Arch Linux package ecosystem, including the official repositories and the AUR, while providing its own installer and system-management tools.

Viridium is designed to keep the parts of Arch that are useful and familiar while making a few parts of the system simpler to use.

vbuild

vbuild is the main package manager in Viridium.

Its primary purpose is combining the official Arch repositories and the AUR into one package-management interface.

On a normal Arch installation, package management commonly looks like:

pacman → official repositories
yay    → AUR

Viridium instead uses:

vbuild → official repositories + AUR

This means you don't have to switch between two different programs depending on where a package comes from.

vbuild is also designed around a faster workflow than the traditional pacman + AUR helper setup.

Its command syntax is intentionally similar to pacman, so existing Arch users don't have to learn an entirely different command structure.

vinstall

vinstall is the Viridium installer.

It handles the initial system setup, including:

  • Disk configuration

  • Filesystems

  • Kernel selection

  • Hostname

  • Timezone

  • User creation

  • Base package installation

  • EFI configuration

  • Bootloader installation

It can either wipe an entire disk or install using existing partitions.

viridium

viridium is the general system-management command.

It provides commands for things such as:

viridium update
viridium clean
viridium info
viridium doctor

It also manages the temporary unlocking of pacman and yay.

Package management

Normal package management should be done through vbuild.

For example:

vbuild -S firefox

Update the system with:

vbuild -Syu

Search for a package with:

vbuild -Ss firefox

See vbuild for the full command reference.

Installation

Boot the Viridium live environment and run:

vinstall

See Installation for the complete installation procedure.

Getting help

For system diagnostics:

viridium doctor

For command help:

viridium help

The Troubleshooting page covers common problems and their solutions.

Installation

Viridium is installed using vinstall from the live environment.

Requirements

Before starting the installation, make sure the system has:

  • UEFI firmware
  • A working internet connection
  • A disk or existing partition to install to

    • The installer downloads packages during installation, so an internet connection is required.

    Starting the installer

    Boot the Viridium live environment and run:

    vinstall

    The installer will guide you through the required configuration.

    Installation steps

    The installer asks for several pieces of information before installing the system.

    Kernel

    Select the kernel to install.

    The selected kernel is installed into the new system and used for normal booting.

    Hostname

    Enter the hostname for the new system.

    This becomes the system hostname after installation.

    Timezone

    Select the timezone to use.

    The selected timezone is configured in the installed system.

    Username

    Enter the username for the initial user account.

    The account is created during installation and configured for sudo.

    Disk configuration

    Viridium supports two main disk configuration modes.

    Wipe the entire disk

    The installer creates the required partition layout and uses the selected disk for Viridium.

    Use this mode when Viridium is going to be the only operating system on the disk.

    **This is destructive.**

    The installer requires a typed confirmation before performing destructive operations.

    Double-check the selected disk before confirming.

    Use existing partitions

    Existing partitions can be selected instead of wiping the disk.

    The installation requires:

  • A root filesystem partition
  • An EFI System Partition

    • This mode is useful for dual-boot installations or systems where the disk has already been partitioned.

    Dual boot

    Viridium can use an existing EFI System Partition.

    For example, a system might already contain:

    EFI System Partition
├── Microsoft
└── existing Linux boot files

    Viridium can install its boot files into the same EFI System Partition.

    Existing boot entries are not removed by the installer. A Windows installation can therefore remain alongside Viridium.

    EFI System Partition

    The EFI System Partition must be mounted during installation.

    The installer handles the required EFI configuration.

    See Boot and UEFI for more information about Viridium's boot setup.

    Filesystems

    The root partition selected during installation is used as the filesystem for the installed system.

    The installer handles mounting the selected partitions while the installation is running.

    Network

    The installer requires network access because packages are downloaded during the installation.

    NetworkManager is used for network configuration.

    If the live environment does not have a working connection, use:

    nmtui

    to configure Wi-Fi.

    Installation completion

    After all packages and configuration have been installed, the installer finishes and the system can be rebooted.

    Remove the installation media before booting the new installation.

    First boot

    The installed system boots through systemd-boot on UEFI systems.

    Log in using the user created during installation.

    On the first login, Viridium displays a one-time message explaining the package-management setup.

    The message explains the relationship between:

  • vbuild
  • pacman
  • yay

    • It is only shown once.

    After installation

    A good first check is:

    viridium info

    Then check the system:

    viridium doctor

    To update the newly installed system:

    viridium update

    See vbuild for package-management commands.

    Configuration

    Viridium uses the standard Linux configuration tools and system components wherever possible.

    Hostname

    The hostname can be viewed with:

    hostnamectl

    The hostname is normally configured during installation.

    Timezone

    The current timezone can be checked with:

    timedatectl

    The timezone is selected during installation.

    Users

    The initial user is created by vinstall.

    The account is configured for sudo.

    Normal Linux user-management tools can be used after installation.

    Services

    Viridium uses systemd for service management.

    Check a service with:

    systemctl status service-name

    List failed services:

    systemctl --failed

    List enabled services:

    systemctl list-unit-files --state=enabled

    Network configuration

    Network configuration is handled by NetworkManager.

    See Networking.

    Package configuration

    Packages should normally be installed and removed through:

    vbuild

    Direct pacman and yay access is locked by default.

    See Package Management.

    vbuild

    vbuild is Viridium's primary package manager.

    It provides a single interface for packages from both the official Arch repositories and the AUR.

    Why vbuild exists

    Arch Linux separates its official repositories from the AUR.

    A common setup therefore uses:

    pacman → official repositories
yay    → AUR

    Viridium combines these into:

    vbuild → official repositories + AUR

    This is the main reason vbuild exists.

    A package does not need a different command simply because it comes from the AUR.

    vbuild is also designed to be faster than the traditional workflow of using pacman and then a separate AUR helper.

    Command syntax

    vbuild uses command-line options similar to pacman.

    This is intentional.

    Users familiar with Arch should already recognize most of the common operations.

    Installing packages

    Install a package with:

    vbuild -S package

    For example:

    vbuild -S firefox

    The package can come from the official repositories or the AUR.

    Searching for packages

    Search for a package with:

    vbuild -Ss search-term

    For example:

    vbuild -Ss firefox

    This is useful when the exact package name is not known.

    Updating the system

    Update the system with:

    vbuild -Syu

    This updates installed packages using the configured package sources.

    Removing packages

    Remove a package with:

    vbuild -Rns package

    This removes the selected package and cleans up dependencies that are no longer required.

    For example:

    vbuild -Rns firefox

    Cleaning orphaned packages

    Remove orphaned packages with:

    vbuild -Yc

    An orphaned package is a package that is no longer required by another installed package.

    Common commands

    Command | Description -- | -- vbuild -S package | Install a package vbuild -Ss term | Search for packages vbuild -Syu | Update the system vbuild -Rns package | Remove a package vbuild -Yc | Remove orphaned packages

    AUR packages

    AUR packages are handled through the same vbuild interface as packages from the official repositories.

    This is one of the main differences between Viridium's package-management workflow and a normal Arch setup.

    There is normally no need to run an AUR helper separately.

    pacman and yay

    pacman and yay are locked by default in Viridium.

    This prevents package management from being split between several different tools.

    Normal package operations should go through:

    vbuild

    If pacman or yay is run directly, Viridium can detect the command and provide the corresponding vbuild command.

    Unlocking the original tools

    There are cases where the original tools are required.

    For example, a development script may expect normal pacman behaviour.

    They can be temporarily unlocked with:

    sudo viridium unlock

    A custom unlock period can be specified:

    sudo viridium unlock 30

    The number is the unlock duration in minutes.

    To lock the tools again manually:

    sudo viridium lock

    The tools automatically lock again when the unlock period expires.

    vbuild vs pacman + AUR helper

    The intended package-management layout is:

    Traditional Arch:

    pacman
      │
      └── official repositories
    

    yay
      │
      └── AUR
    

    Viridium:
    

    vbuild
      ├── official repositories
      └── AUR

    The unified setup is the main purpose of vbuild, while the faster workflow is an additional part of its design.

    viridium

    viridium is Viridium's general system-management utility.

    While vbuild is responsible for package management, viridium handles system-level tasks that don't belong directly in the package manager.

    It provides shortcuts for common maintenance tasks, system information, diagnostics, and control over Viridium's package-management restrictions.

    Usage

    The general syntax is:

    viridium <command>

    Run:

    viridium help

    to display the available commands.

    Commands

    update

    viridium update

    Updates the system using vbuild.

    This is a shortcut for:

    vbuild -Syu

    Using viridium update is intended for users who want a simple system-update command without having to remember the underlying vbuild options.

    clean

    viridium clean

    Cleans up unused package data, including orphaned packages.

    This is a shortcut for:

    vbuild -Yc

    It is useful for routine system maintenance and freeing up space that is no longer needed by installed packages.

    info

    viridium info

    Displays basic information about the current Viridium installation.

    Information includes:

    • Kernel

    • Hostname

    • Uptime

    • Installed package count

    This is intended as a quick overview rather than a complete hardware or system-information utility.

    doctor

    viridium doctor

    Runs a series of checks against the current system.

    The checks cover common problems such as:

    • DNS

    • Disk space

    • Orphaned packages

    • Failed services

    • Other basic system conditions

    The output is intended to be readable and useful without requiring the user to manually check every component.

    doctor --fix

    viridium doctor --fix

    Runs the normal diagnostic checks and attempts to fix problems that can be safely handled automatically.

    Problems that cannot be safely fixed are reported instead.

    --fix should not be treated as a replacement for manually diagnosing serious system problems.

    pacman and yay control

    viridium also controls the default lock on pacman and yay.

    Viridium normally expects package management to go through vbuild.

    unlock

    sudo viridium unlock

    Temporarily unlocks the original pacman and yay commands.

    A custom timeout can be supplied:

    sudo viridium unlock 30

    The number specifies the unlock duration in minutes.

    lock

    sudo viridium lock

    Immediately re-locks pacman and yay.

    An unlock also expires automatically when its timeout is reached.

    Why this is separate from vbuild

    vbuild is focused on packages.

    viridium is focused on the rest of the system.

    Keeping these responsibilities separate means package operations can remain inside vbuild, while system maintenance and administrative functions can be provided through viridium.

    In practice:

    vbuild
    └── Package management

    viridium
        ├── System maintenance
        ├── Diagnostics
        ├── System information
        └── Package-manager control

    Command summary


    Command | Description
-- | --
viridium help | Display available commands
viridium update | Update the system
viridium clean | Clean unused package data
viridium info | Display system information
viridium doctor | Run system diagnostics
viridium doctor --fix | Run diagnostics and fix supported problems
sudo viridium unlock | Temporarily unlock pacman and yay
sudo viridium unlock  | Unlock for a specified period
sudo viridium lock | Lock pacman and yay immediately

    Architecture

    Viridium is built around the Arch Linux package ecosystem with a small set of custom tools layered on top.

    The project does not attempt to replace the underlying Arch system. Instead, Viridium provides its own installation and management workflow while continuing to use the existing Arch infrastructure.

    Overview

    The main components are:

                             Viridium Linux
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
          Installation                         System
              │                                   │
          vinstall                     ┌───────────┴───────────┐
                                       │                       │
                                    vbuild                 viridium
                                       │                       │
                              ┌────────┴────────┐       ┌──────┴──────┐
                              │                 │       │             │
                         Arch repos            AUR   Maintenance   Diagnostics

    Each component has a specific purpose.

    vinstall

    vinstall is responsible for creating a Viridium installation.

    Its responsibilities include:

    • Disk selection

    • Partition handling

    • Filesystem setup

    • Kernel installation

    • Base system installation

    • Hostname configuration

    • Timezone configuration

    • User creation

    • sudo configuration

    • EFI configuration

    • Bootloader installation

    The installer runs from the Viridium live environment and installs the system onto the selected disk or existing partitions.

    It is not responsible for normal system management after installation.

    vbuild

    vbuild is the package-management layer.

    Its main purpose is combining the two package sources used by Viridium:

    Official Arch repositories
            +
           AUR
            ↓
         vbuild

    A traditional Arch setup often separates these:

    pacman → official repositories
yay    → AUR

    Viridium provides one interface instead.

    Package management flow

    A simplified package-management flow is:

    User
 │
 ▼
vbuild
 │
 ├──► Official repositories
 │
 └──► AUR

    This is the central design decision behind vbuild.

    It also allows Viridium to implement a faster package-management workflow than the traditional pacman + AUR helper setup.

    viridium

    viridium sits above the lower-level system tools.

    It provides commands for:

    • Updating

    • Cleaning

    • Diagnostics

    • System information

    • Package-manager locking

    • Package-manager unlocking

    It can also act as a simple frontend for common vbuild operations.

    For example:

    viridium update
       │
       ▼
vbuild -Syu

    The purpose is to provide simple commands for common operations without adding another package-management implementation.

    pacman and yay

    The original Arch package tools still exist underneath the Viridium package-management system.

    They are locked by default rather than removed.

    The relationship is therefore:

                        Package management
                           │
                         vbuild
                       /       \
                      /         \
             Arch repositories   AUR
                      
              pacman / yay
                    │
             compatibility /
              temporary use

    viridium controls whether the original tools are accessible.

    They can be temporarily unlocked when compatibility, development, or debugging requires them.

    NetworkManager

    Viridium uses NetworkManager for network configuration.

    NetworkManager is separate from the Viridium package-management tools and provides the normal Linux networking layer.

    Common interfaces include:

    nmtui
nmcli

    systemd

    Viridium uses systemd for system initialization and service management.

    This includes normal systemd functionality such as:

    systemctl

    Services can therefore be managed using the standard systemd tools.

    systemd-boot

    Viridium uses systemd-boot for UEFI booting.

    The installer places the required boot files on the EFI System Partition and creates the Viridium boot entry.

    Existing EFI entries can remain alongside it.

    Design principles

    Viridium's architecture is based around a few simple ideas.

    Keep the Arch ecosystem

    Viridium does not need to maintain a completely separate package ecosystem.

    The Arch repositories and AUR already provide the packages required by the system.

    One package manager

    Normal package management goes through vbuild.

    This combines the official repositories and AUR and avoids requiring separate tools for normal package operations.

    Keep system tools separate

    vinstall, vbuild, and viridium have different responsibilities.

    vinstall   → installation
vbuild     → packages
viridium   → system management

    This separation keeps each component relatively focused.

    Don't remove the underlying tools

    Viridium does not permanently remove pacman or yay.

    They remain available for compatibility and development purposes, but are locked during normal operation.

    Component summary

    Component | Responsibility -- | -- vinstall | Installation vbuild | Package management viridium | System management pacman | Underlying Arch package manager yay | AUR helper / compatibility NetworkManager | Networking systemd | System and services systemd-boot | UEFI boot

    This separation is the basis of the Viridium userspace.

    Boot and UEFI

    Viridium currently uses UEFI booting and systemd-boot.

    UEFI

    Viridium requires a UEFI-capable system.

    Legacy BIOS/CSM installation is not supported by the installer.

    EFI System Partition

    The EFI System Partition contains the boot files required to start Viridium.

    When installing with existing partitions, an existing EFI System Partition can be reused.

    This is particularly useful for dual-boot systems.

    Dual boot

    Viridium can share an EFI System Partition with other operating systems.

    For example:

    EFI System Partition
├── Microsoft
└── Viridium

    The installer does not remove existing boot entries.

    A Windows Boot Manager entry can therefore remain alongside the Viridium boot entry.

    systemd-boot

    Viridium installs systemd-boot as its UEFI bootloader.

    The bootloader is installed to the EFI System Partition selected during installation.

    Checking boot entries

    From a working Linux installation, EFI boot entries can be inspected with:

    efibootmgr

    The Viridium entry should be present after a successful installation.

    Boot problems

    If Viridium does not boot, check:

    1. The firmware is running in UEFI mode.
    2. The EFI System Partition exists.
    3. The correct EFI partition was used during installation.
    4. The Viridium boot entry exists.
    5. The firmware has not disabled or removed the entry.

    For further diagnostics, boot another Linux environment and inspect the EFI configuration.

    Development

    This page covers development of Viridium itself.

    Viridium is made up of several components rather than being a single program. Changes should generally be made to the component responsible for the affected functionality.

    Repository

    The Viridium source code is maintained in the project's Git repository.

    The repository contains the installer, package-management components, system-management utilities, and supporting files required to build the distribution.

    Main components

    vinstall

    vinstall contains the installation logic.

    Changes to this component can affect:

  • Partitioning
  • Filesystems
  • Kernel installation
  • User creation
  • System configuration
  • EFI setup
  • Bootloader installation
  • Package installation

    • Installer changes should be tested carefully because errors can affect the target disk.

    vbuild

    vbuild contains the package-management logic.

    It is responsible for the unified package workflow between:

    Official repositories
        +
       AUR
        ↓
     vbuild

    Changes to vbuild should be tested against both package sources.

    Package installation, searching, updating, removal, and dependency handling are particularly important areas to test.

    viridium

    viridium contains the higher-level system-management commands.

    This includes:

  • update
  • clean
  • info
  • doctor
  • doctor --fix
  • unlock
  • lock

    • Changes should be checked both directly and through the commands that call other Viridium components.

    Development workflow

    A typical development cycle is:

    Change code
    │
    ▼
Build
    │
    ▼
Test
    │
    ▼
Fix issues
    │
    ▼
Test again
    │
    ▼
Commit

    Do not assume that a successful build means the change works correctly. Installer and package-management changes in particular need to be tested in an actual installation environment.

    Testing

    Installer testing

    Installer changes should preferably be tested in a virtual machine or on a dedicated test disk.

    This is especially important for changes involving:

  • Partitioning
  • Filesystem creation
  • Mounting
  • EFI partitions
  • Bootloader installation
  • Disk detection

    • Testing these changes directly against a normal installation can result in data loss if something goes wrong.

    Package manager testing

    vbuild should be tested with both official repository packages and AUR packages.

    Basic tests include:

    vbuild -Ss package
vbuild -S package
vbuild -Syu
vbuild -Rns package
vbuild -Yc

    Tests should also cover packages that have dependencies and packages that are already installed.

    viridium testing

    The common commands should be tested individually:

    viridium update
viridium clean
viridium info
viridium doctor
viridium doctor --fix

    The locking system should also be tested:

    sudo viridium unlock
sudo viridium lock

    and with a custom timeout:

    sudo viridium unlock 30

    Testing pacman and yay handling

    Because pacman and yay are intentionally restricted, changes to their handling should be tested carefully.

    At minimum, verify:

    1. Direct use is blocked normally.
    2. The user receives the appropriate replacement information.
    3. vbuild continues to work normally.
    4. viridium unlock enables the original tools.
    5. viridium lock disables them again.
    6. The automatic timeout works.
    7. A custom timeout works.

    Development environments

    For major installer or boot changes, a virtual machine is preferred.

    A VM allows the complete installation process to be tested without modifying a normal installation.

    For smaller changes to vbuild or viridium, development can be performed on an existing Viridium installation as long as the changes are tested carefully.

    Debugging

    When debugging a component, first determine which layer is responsible.

    For example:

    Installation problem
        ↓
     vinstall

Package problem
        ↓
      vbuild

System-management problem
        ↓
    viridium

Service problem
        ↓
     systemd

Network problem
        ↓
 NetworkManager

Boot problem
        ↓
    EFI / systemd-boot

    This helps avoid changing the wrong component to fix a problem that originates somewhere else.

    Code changes

    Keep changes focused on the component being modified.

    For example, package-management behaviour should normally be implemented in vbuild rather than duplicated inside viridium.

    Likewise, viridium update should call the package-management functionality rather than implementing another update system.

    This keeps the project from accumulating multiple implementations of the same operation.

    Documentation

    When adding or changing a user-facing feature, update the relevant wiki page.

    The documentation should describe:

  • What the feature does
  • Why it exists
  • How to use it
  • Relevant commands
  • Important limitations
  • Any compatibility considerations

    • Commands should be shown as runnable examples where possible.

    Releases

    Before a release, test the main system paths:

    Live environment
      ↓
   vinstall
      ↓
 Installed system
      ↓
    vbuild
      ↓
 Package management
      ↓
  viridium
      ↓
Maintenance / diagnostics

    A release should at minimum be able to:

  • Install successfully
  • Boot successfully
  • Create and log into a user
  • Connect to the network
  • Install packages
  • Search for packages
  • Update packages
  • Remove packages
  • Handle AUR packages
  • Run viridium doctor
  • Lock and unlock pacman/yay

    • Development priorities

    Viridium's development is primarily focused on keeping the system simple and consistent.

    New features should fit into the existing architecture instead of creating another separate way of doing something that Viridium already handles.

    The basic separation should remain:

    vinstall
    installation

vbuild
    package management

viridium
    system management

    Networking

    Viridium uses NetworkManager for network configuration.

    NetworkManager is enabled by default.

    nmtui

    nmtui provides a terminal-based interface for NetworkManager.

    Start it with:

    nmtui

    It can be used to connect to Wi-Fi and configure network connections without manually entering the required nmcli commands.

    nmcli

    nmcli is available for direct command-line network management.

    It is useful for scripting, automation, and users who prefer not to use the interactive interface.

    Checking NetworkManager

    Check the NetworkManager service with:

    systemctl status NetworkManager

    If necessary, restart it with:

    sudo systemctl restart NetworkManager

    Checking DNS

    Viridium's diagnostic tool can check common DNS problems:

    viridium doctor

    The current resolver state can also be inspected with:

    resolvectl status

    No network connection

    If Wi-Fi is not connected, start:

    nmtui

    and select the required network.

    If NetworkManager itself appears to be stopped:

    systemctl status NetworkManager

    Restart it if necessary:

    sudo systemctl restart NetworkManager

    If the problem is still unclear:

    viridium doctor

    Package Management

    Viridium uses vbuild as its normal package-management interface.

    Package sources

    Viridium uses the same general package ecosystem as Arch Linux:

  • Official Arch repositories
  • Arch User Repository (AUR)
    • vbuild handles both sources.

    Official repositories

    Packages available through the normal Arch repositories are installed through vbuild:

    vbuild -S package

    AUR

    Packages available through the AUR are also handled through vbuild.

    The user does not need to switch to yay or another AUR helper for normal package installation.

    Package management model

    The intended model is:

                     vbuild
                /      \
               /        \
      Arch repositories  AUR

    rather than:

    pacman ──→ Arch repositories
yay ─────→ AUR

    This provides one entry point for package management.

    Why pacman and yay are locked

    pacman and yay are disabled for normal direct use.

    The purpose is to prevent multiple package-management paths from being used at the same time.

    For example, a normal Viridium system should generally be managed through:

    vbuild -Syu

    rather than independently running pacman and yay.

    This also allows Viridium's package-management workflow to remain consistent.

    Command translation

    If a user runs pacman or yay directly, Viridium can detect the command and provide the equivalent vbuild command.

    This makes accidentally using the wrong command less disruptive.

    Unlocking

    When direct access to the original tools is actually required:

    sudo viridium unlock

    A custom duration can be specified:

    sudo viridium unlock 30

    Lock them immediately with:

    sudo viridium lock

    The tools automatically lock again after the timeout.

    When should pacman or yay be unlocked?

    The normal answer is: only when something specifically requires them.

    Examples include:

  • Testing package-management behaviour
  • Development
  • Scripts expecting the original commands
  • Debugging package-manager issues

    • For normal package installation and updates, use vbuild.

    Troubleshooting

    This page covers some of the more common problems encountered while using Viridium.

    Start with viridium doctor

    For general problems, run:

    viridium doctor

    It checks several common system conditions and reports anything it finds.

    If supported fixes are available:

    viridium doctor --fix

    No network connection

    Check NetworkManager:

    systemctl status NetworkManager

    If it is not working correctly:

    sudo systemctl restart NetworkManager

    For Wi-Fi:

    nmtui

    DNS problems

    Run:

    viridium doctor

    You can also inspect the resolver configuration:

    resolvectl status

    Low disk space

    Check the system:

    viridium doctor

    Then clean unused package data:

    viridium clean

    Or directly:

    vbuild -Yc

    Orphaned packages

    Remove orphaned packages with:

    viridium clean

    or:

    vbuild -Yc

    Failed services

    List failed systemd services:

    systemctl --failed

    Check a specific service with:

    systemctl status service-name

    pacman or yay will not run

    This is expected behaviour.

    Both commands are locked by default.

    Use:

    vbuild

    for normal package management.

    If the original tool is actually required:

    sudo viridium unlock

    Package installation problems

    First check the network:

    viridium doctor

    Then retry the package operation.

    For example:

    vbuild -S package

    If the issue involves the underlying package tools, they can be temporarily unlocked for further testing.

    Boot problems

    If the system does not boot, see Boot and UEFI.

    From another Linux environment, EFI boot entries can be checked with:

    efibootmgr

    Installation problems

    If installation fails, check:

  • Network connectivity
  • Selected disk
  • EFI System Partition
  • Available disk space
  • Installer output

    • Do not retry a destructive installation without checking which disk is selected first.

    Frequently Asked Questions

    Is Viridium actually Arch?

    Viridium is Arch-based and uses the Arch package ecosystem, including the official repositories and AUR.

    The main differences are Viridium's installer and management tools.

    Does Viridium use the AUR?

    Yes.

    AUR packages are handled through vbuild.

    Do I need yay?

    No.

    vbuild is designed to handle both official repository packages and AUR packages.

    Why was vbuild created?

    The main reason is to combine the official Arch repositories and the AUR into one package manager.

    It also uses a faster package-management workflow than the traditional pacman + AUR helper setup.

    Can I still use pacman?

    Yes.

    pacman is locked by default, but it can be temporarily unlocked: 
    sudo viridium unlock

    Can I still use yay?

    Yes.

    yay is also locked by default and can be temporarily unlocked in the same way.

    Why are pacman and yay locked?

    Viridium is designed around vbuild being the single normal entry point for package management.

    Allowing three different package-management paths would defeat the purpose of combining the official repositories and AUR.

    Does Viridium replace Arch's packages?

    No.

    Viridium uses the Arch package ecosystem rather than maintaining an entirely separate package ecosystem.

    Does Viridium support dual boot?

    Yes.

    An existing EFI System Partition can be reused, and existing boot entries are left in place.

    What bootloader does Viridium use?

    Viridium uses systemd-boot on UEFI systems.

    Does Viridium use systemd?

    Yes.

    How do I update?

    Either:

    vbuild -Syu

    or:

    viridium update

    How do I clean the system?

    viridium clean

    or:

    vbuild -Yc

    How do I check for problems?

    viridium doctor

    For automatic fixes where supported:

    viridium doctor --fix

    How do I connect to Wi-Fi?

    Run:

    nmtui

    Where should I start if something is broken?

    Run:

    viridium doctor

    Then check the relevant page in this wiki.
